## Learnings

- Purpose: the HTTP layer over `store.Store` — HTML pages, JSON endpoints, an SSE stream, opencode session management, and the docs refresh queue. Handlers branch on `wantsHTML`/`isHX`/`isJSON` (JSON default); optional integrations are nil-disabled (`s.oc`, `s.docsQ`) — guard and return 503; tests use fixture stores and fake clients (`SetOpencode` around an httptest-backed `opencode.New`, `SetDocsRunner` injectable). Key files: `server.go` holds `Server` and the route table; `mapping.go` owns `.lessmess/sessions.json`; `docsqueue.go` plus `docssession.go` drive doc gardening; `render.go` owns templates and static assets; `touched.go` extracts covered dirs from tasks' "Files affected".
- Sessions are primed at creation: `changePrime`/`taskPrime`/`discussionPrompt` render the embedded instruction modules for their audience (`renderPrime`) with the session's own ID in the prime context — the `change.handoff` module bakes it into the sanctioned spawn curl — a prime failure deletes the session and returns 502 so nothing unbound leaks, scaffold refuses an already-bound session with a 409 whose agent-facing message teaches the handoff path, binding is absolute and applies only to new sessions, and the discussion prompt's step-0 empty state is pinned by tests. Unbound sessions prime purpose prompts instead: `chatSession` (`POST /chat/session`, the header Chat button) renders the sole `chat`-audience module over an empty `primeContext` — a repo-root free agent that edits on explicit request and never touches workflow state — its composition and empty-context render are pinned, and the session lands in the unassigned Discussions bucket like explorer chats, behind the same guards (503 without opencode or a readable mapping). A discussion session is read-only before scaffold, then plans the tracked change and may execute in the same session after explicit user approval; prompts reach only sessions created after an instruction change.
- Chat is the sole session interface and the browser never talks to the OpenCode service directly: the session surface is the explicit `/api/sessions/{sessionID}/chat*` route family in `chat.go` (snapshot, tool detail, diff, attachments, prompt, references, controls and usage, interrupt, agent/model/command/skill, permission and form replies) plus `sessionlifecycle.go`'s fork/revert/compact/inbox/rename/export/delete endpoints, all calling the service server-side so credentials never reach browser responses or JS — there is no generic pass-through. Transcript freshness is a full snapshot on open/reconnect plus polling while the view is visible (deliberately no event-stream subsystem for chat; `/events` stays board/docs-only), the server normalizes service parts into view models with unknown-part fallbacks, capability-gated operations surface `opencode.ErrCapabilityUnavailable` as a 503, and the embedded terminal is fully removed with tests pinning its absence.
- The handoff spawn is the one sanctioned new-change-from-a-bound-change flow: `POST /changes/{id}/spawn-change` (`spawnChange`) guards 404 unknown change → 503 no opencode/unreadable mapping → 400 bad JSON → 422 shape (`prefixRe` for title/prefix; artifact must be a bare existing `handoff*.md` at the source change's root, worktree-aware) → 409 when a supplied caller session is bound elsewhere (an absent session is a board call); change B is created first and never rolled back, B's session primes with the change modules plus a handoff addendum (task files and ledger rows in the same pass, validator run before implementation) and binds with `SpawnedFrom` = source change, and a prime failure deletes the session and returns 502 naming B; `GET /changes/{id}/handoffs` lists sorted `handoff*.md` basenames for the picker (`{"handoffs":[]}` when none).
- The nested task surface lives here: `GET /changes/{id}/tasks/{file...}`, `POST /changes/{id}/expand` (409 when the container exists), `POST /changes/{id}/tasks` with optional `parent` (API-only — no board form posts to it), `?task=` drill-down boards with breadcrumbs, recursive counts via `SubtreeStats`, and close gated on `store.CloseOutReady`. The deterministic task-state endpoints (`taskstate.go`: status, update, reorder, decisions) enforce the workflow rules server-side — `Done` is user-gated on the `X-Lessmess-UI` header (403 for agents, who stop at `Test`) and `Test` requires verification evidence (422).
- Subagent sessions bind at every tree node: `taskTitleRe` matches dotted IDs, `reconcileTaskSessions` (run from `listChangeSessions` and the Chat navigation endpoint) walks descendants through paginated `ListChildrenPage` (cycle- and duplicate-safe) and additively binds only unmapped descendants whose title names a task — other subagents remain transient helpers visible in Chat's Agents hierarchy and never become workflow sessions, `bindTaskSession` is the corrective bind with guard order 422 → 409 → 200 idempotent → 201, `SessionEntry` carries optional `task`/`parent`/`spawnedFrom`/`modules` (`omitempty`), and auto-spawn is once per container via `.lessmess/autosession.json` — a failed spawn leaves the marker unset for the next sweep, a session bound by any other means (delegation, manual bind) marks the node done, and unlinking never respawns.
- The index sorts newest-first server-side (date prefix descending, then workflow-index position descending — entries are append-mostly, so a later position is newer — then ID ascending; IDs under ten characters sort last) — pinned by `TestIndexNewestFirst`; `statusRank` in `templateFuncs` maps `model.TaskStatusOrder` with `len` as the unknown-status fallback, client-side sorting persists to localStorage, and the server's only job is emitting `data-*` keys, never scraping display text. Overall-status writes are close/reopen only — there is no free-form status endpoint: `POST /changes/{id}/close` (`lifecycle.go`) gates on `store.CloseOutReady` (422 naming offenders), then the worktree pipeline, then `store.SetChangeStatus` (`Done` in the state file) plus the best-effort docs auto-gardener, and `POST /changes/{id}/reopen` sets In progress.
- All user-visible markdown renders through the shared goldmark instance in `render.go` (auto heading ids + GFM tables — bare `goldmark.New()` gives neither); plan/ledger detail handlers render an HTML partial vs JSON on `wantsHTML`/`isHX`; `dropLeadingH1` and other presentation trims stay server-side, while TOC, scroll-spy, and `.md` link interception are client-side in `app.js`.
- The explorer is the docs-system UI (`explorer.go`): `/explorer` page, `/explorer/tree` fragment, `/explorer/detail` per-directory pane, `/explorer/chat` root-scoped session mapped to unassigned Discussions; detail re-walks and validates (`.` is root, 503 without docs, 422 uncovered/missing, 404 absent); `docswatch.go` merges debounced fsnotify events into `/events` as kind `docs`, ignoring hidden files, `.tt-` temp files, and attribute-only `CHMOD` (macOS atime from render-time git scans).
- Git awareness is read-only in Go: `gitcommit.go` shells out for status preview (`GET /api/git/status`), `POST /api/git/commit` re-checks dirtiness then primes a repo-wide `repoCommitPrompt` session, both flows share the `commitStatus` poller, and `indexView` computes `GitRepo`/`GitDirty` at render time — the actual commit always happens inside an opencode session.
- The gardener runs a whole-tree skeleton refresh then one session per job; confinement requires out-of-marker bytes to equal the pre-pass snapshot, the meta hash to match the walked tree, no snapshot deletions, and markers on any created `AGENTS.md` — violations restore and flag stale. `gardenerPrompt` renders update dirs plus a REVIEW-AND-FIX section for `coveredAncestors` (fix/delete license, reply must account for every removal); manual jobs stay single-section with lint-flagged refs named; learnings are consolidated in place — current-state phrasing, no provenance prefixes, at most 15 per file. `.lessmess/docs-queue.json` holds pending/stale atomically; a missing runner fails a job straight to stale; both enqueue paths chunk at `docsJobMaxDirs` (3) — close-out jobs split the touched dirs into consecutive chunks whose `coveredAncestors` are deduped across chunks (first claim wins, so every dir is updated or reviewed exactly once across the change's jobs) and manual refresh chunks its stale/hash/lint union — while each job's context budget scales through `jobTimeout` (15 minutes base plus 5 minutes per Dir+Ancestor target), so a timeout flags and reverts only its own chunk and the queue moves on to the next; successful jobs persist their stale clears, so a restart cannot resurrect flags for dirs the job just refreshed.
- Settings live entirely in this package: `settings.go` owns the stateless layered load/merge (project `lessmess.json`, personal `.lessmess/settings.json`, tri-state fields), `settingsapi.go` serves `/settings` + `/api/settings` and validates agent/model against the live service at save (422; skipped when unreachable — creation itself never validates, it de-escalates on a 400 instead), `settingschange.go` keeps one active per-field discussion via `.lessmess/settings-change.json`, `opendefault.go` reads the served repo's `opencode.json` `default_agent` into the payload (`opencodeDefaultAgent`, present only when declared; missing file/empty key is `absent`, JSONC/non-plain-JSON is `unreadable`, failures degrade to no notice) and serves Align `POST /api/settings/opencode-default-agent` — live validation (422 unknown/empty agent, 503 unreachable; stricter than save), existing key required, only that value rewritten byte-preserving via `model.WriteFileAtomic`, and `settingsFieldValue`'s dotted-path allowlist must extend in lockstep with `EffectiveSettings`. `general.projectName` never stores its default: effective reads (`loadEffectiveSettings`/`effectiveProjectName`) compute the `filepath.Base(repoDir)` fallback (guarded to `lessmess`) at read time, the sources map keeps reporting `default` while unset, and `settingsResponse.defaultProjectName` exposes that folder default to the UI.
- `spawnSessionWithModel` (`settings.go`) de-escalates on a 400 `opencode.APIError` — agent+model → agent-only → model-only → plain, built from whatever is actually configured and always ending in plain so a bad setting never blocks spawning; any other error returns immediately, every dropped piece logs a warning, and `spawnfallback.go` records the outcome (attempted agent/model, winning step, service error) in `.lessmess/spawn-fallback.json` — best-effort write on a de-escalated success, removed whenever the first attempt succeeds, read fail-open so a malformed record never breaks the index; `indexView` renders the board banner from it at render time, the same pattern as `GitDirty`.
- The accent system rolls once: `accent.go` is the only palette source, `ResolveAccent` persists a random pick through `persistAccent` (whole `ui` section — `applySettingsPatch` replaces sections), unknown stored ids fail open to the default without a rewrite, and `ui.accent` validation is offline and always enforced (unlike agent/model). `brandassets.go` serves `/icon.svg`, `/favicon.ico`, and `/apple-touch-icon.png` rendered per accent with accent-id ETags and `no-cache` 304 revalidation; the setup mux mounts the same routes over the no-roll `effectiveAccentColor` read path (no store in setup mode), and `render()` fills `pageData.AccentStyle` and `pageData.ProjectName` centrally through the wired `accent`/`projectName` hooks (both wired in `server.New` and `NewSetup`), so handlers never touch either.
- Setup mode gates solely on `store.ErrNoChanges`: `NewSetup` serves the wizard plus `/api/setup/*` on both muxes (everything else 503/redirect), bootstrap hot-swaps the full handler in-process, prereq probe seams are package-level fakes (only `fail` blocks), onboarding state in `.lessmess/onboarding.json` fails open, and the docs-seed endpoints share one in-flight registry plus the `.lessmess/docs-seed.json` cursor (409 while running, 503 without opencode or coverage).
