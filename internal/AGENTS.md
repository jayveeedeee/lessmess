## Learnings

- Purpose: home of lessmess's Go application packages — `model`, `store`, `docs`, `server`, `opencode`, and `terminal` — all consumed by `cmd/lessmess`. Dependency direction flows inward: `model` is the lowest-level parser/serializer, `store` builds on it, and `server` builds on `store` plus `docs`, `opencode`, and `terminal`.
- Each package in this tree has its own `AGENTS.md` with package-specific notes; read it before editing code in the package — these notes are only the cross-package map.
- The `changes/` tree is canonical data that these packages never own: mutations re-read on-disk content and write atomically via `model.WriteFileAtomic`, so external edits are never clobbered.
- Verify changes from the repo root with `go vet ./...` and `go test ./...`.
- `os/exec` use is confined to three packages: `server` (`gitcommit.go`, read-only `git` status/diff for preview), `opencode` (background service status), and `terminal` (PTY); actual commits happen inside primed opencode sessions, not in Go.
- The docs-system work splits in two: `docs` owns coverage config, tree walking, STRUCTURE.md generation/validation, and seed orchestration, while `server` owns the refresh queue, gardener runner, docs watcher, and explorer handlers. The subsystem is inert without a root `agentsdocs.json` (`docs.LoadConfig` returns nil, consumers no-op) — guard new code on a non-nil config.
- The module is `lessmess` (renamed from tasktracker), so every package imports its siblings as `lessmess/internal/<pkg>`; the binary name and state dir were renamed while the workflow file formats and their marker names are unchanged.
- Settings live entirely in `internal/server`: `settings.go` owns the schema, stateless layered load, per-field merge, and atomic single-layer writes; `settingsapi.go` owns the page and JSON endpoints; `settingschange.go` owns per-field Change discussions. Other packages never read settings files directly.
- Settings are stateless and fail-open: each access re-reads root `lessmess.json` and `.lessmess/settings.json`, merging personal over project over built-in defaults, so no watcher is needed and a malformed layer degrades to defaults with a logged warning.
- `.lessmess/` tooling state is split one file per feature, all written via `model.WriteFileAtomic`: sessions.json, docs-queue.json, docs-seed.json, settings-change.json, onboarding.json, autosession.json, spawn-fallback.json, and xdg/opencode/cli.json — follow that pattern for new server-side state rather than a shared grab-bag file. `.lessmess/settings.json` may be absent locally; its absence is normal.
- The server has two entry shells: `server.New` (full server over an initialized repo) and `server.NewSetup` (first-run wizard built when `store.Open` fails with `ErrNoChanges`); both share one boot callback so bootstrap hot-swaps the handler in-process, and code assuming a bootable `changes/` tree must tolerate setup mode.
- Setup seams are package-level vars faked in tests: the `prereqProbe*` functions (`prereqs.go`, checks report ok/warn/fail and only `fail` blocks) and `newSeedSummarizer` (`setupseed.go`, one in-flight `docs.Seed` job per repo with in-memory progress lines).
- Serving a change doc is a fixed store+server pair: raw markdown readers in `store` (`PlanFile`, `LedgerFile`, `TaskFile`, `ContainerLedgerFile`) plus `*Detail` handlers in `server` that branch HTML partial vs JSON on `wantsHTML`/`isHX`; presentation-only trims (`dropLeadingH1`) stay in the server so the store returns file content untouched.
- `model.TaskStatusOrder` is the single source of workflow-status order spanning packages: the board's columns render in it and the index table's sortable Status column ranks by it (via `server`'s `statusRank` template func), so a vocabulary change flows through that one slice and its consumers.
- Structural features touch the packages in a fixed order — keep it: nested decomposition runs `model` (dotted-ID helpers, container-ledger parse/render) → `store` (recursive tree, validation, rollup stats, `CloseOutReady`) → `server` (nested routes, drill-down boards, per-task sessions); subagent sessions split `opencode` (raw `ParentID` from the thin client) → `server` (task/parent mapping fields, bind endpoint, reconciler); and all change-overall-status writes centralize in `store.SetChangeStatus` rather than editing ledger files directly.
