# Agent notes: internal

<!-- tasktracker:begin -->
- Purpose: home of lessmess's Go application packages — workflow model, store, HTTP server, docs management, opencode client, and PTY terminal — all consumed by `cmd/lessmess`.
- Dependency direction flows inward: `model` is the lowest-level parser/serializer, `store` builds on it, and `server` builds on `store` plus `docs`, `opencode`, and `terminal`.
- Each subdirectory has its own `AGENTS.md` with package-specific notes; read that file before editing code in the package.
- The `changes/` tree is canonical data that these packages never own: mutations re-read on-disk content and write atomically via `model.WriteFileAtomic`, so external edits are never clobbered.
- Verify changes from the repo root with `go vet ./...` and `go test ./...`.
- (manual) The docs-system work is split across two packages: `docs` owns coverage config, tree walking, STRUCTURE.md generation/validation, and seed orchestration, while `server` owns the refresh queue, gardener runner, docs watcher, and explorer handlers.
- (manual) Each package in this tree — `model`, `store`, `docs`, `server`, `opencode`, and `terminal` — has its own `AGENTS.md`; there are no covered subdirectories beyond those packages.
- (manual) The docs subsystem is inert unless the target repository has a root `agentsdocs.json`; `docs.LoadConfig` returns nil and consumers no-op, so guard any new code on a non-nil config.
- (manual) The module is `lessmess`, so every package here imports its siblings as `lessmess/internal/<pkg>`; the binary name and module were renamed from tasktracker, while the workflow file formats and their marker names are unchanged.
- (manual) `os/exec` use is confined to three packages: `server` (`gitcommit.go`, read-only `git` status/diff for preview), `opencode` (background service status), and `terminal` (PTY); actual commits still happen inside primed opencode sessions, not in Go.
- (manual) Environment-aware spawning is available via `terminal.Manager.SpawnWithEnv` (a nil env inherits the server environment); `server.terminalWS` uses it to inject a generated `XDG_CONFIG_HOME` for chrome-free embedded TUIs.
- (manual) `internal/server/tuiconfig.go` merges the user's `~/.config/opencode/cli.json` with forced chrome-free overrides and is best-effort: parse or write failures log a warning and spawn with the inherited environment instead.
- (manual) The settings subsystem lives entirely in `internal/server`: `settings.go` owns the schema, stateless layered load, per-field merge, and atomic single-layer writes; `settingsapi.go` owns the page and JSON endpoints; `settingschange.go` owns the per-setting Change-button discussions. Other packages never read settings files directly.
- (manual) Settings are stateless and fail-open: each access re-reads root `lessmess.json` and `.lessmess/settings.json`, merging personal over project over defaults, so no watcher is needed and a malformed layer degrades to defaults with a logged warning.
- (manual) `.lessmess/` tooling state is split one file per feature, all written via `model.WriteFileAtomic`: `sessions.json` (session mapping), `docs-queue.json`, `docs-seed.json`, `settings-change.json`, `onboarding.json` (first-run wizard state), `autosession.json` (once-only auto-spawn markers for decomposed tasks, added 2026-09-16-le45q), and `xdg/opencode/cli.json`; follow that pattern for new server-side state rather than adding a shared grab-bag file. The personal settings override is the one optional entry: `.lessmess/settings.json` may be absent locally, and its absence is normal.
- (manual) The server has two entry shells: `server.New` (full server over an initialized repo) and `server.NewSetup` (first-run wizard built when `store.Open` fails with `ErrNoChanges`); both share one boot callback so bootstrap hot-swaps the wizard for the full handler in-process, and code assuming a bootable `changes/` tree must tolerate setup mode.
- (2026-09-15-0) Serving a change doc is a fixed store+server pair: a raw markdown reader in `store` (`PlanFile`, `LedgerFile`) plus a `*Detail` handler in `server` that branches HTML partial vs JSON on `wantsHTML`/`isHX`; presentation-only trims (`dropLeadingH1`) stay in the server so the store returns file content untouched.
- (2026-09-15-lk9or) `model.TaskStatusOrder` is the single source of workflow-status order spanning packages: the board's columns render in it and the index table's sortable Status column ranks by it (via `server`'s `statusRank` template func), so a vocabulary change flows through that one slice and its consumers.
- (2026-09-16-le45q) Nested task decomposition spans the packages in strict order: `model` owns the dotted-ID helpers plus container-ledger parse/render, `store` owns the recursive tree, validation, rollup stats, and `CloseOutReady`, and `server` owns the nested routes, drill-down boards, and per-task sessions — a structural change to the task format must touch all three in that order.
