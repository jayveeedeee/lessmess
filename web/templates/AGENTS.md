# web/templates

<!-- tasktracker:begin -->
- Purpose: Go `html/template` sources for the lessmess web UI; each file defines named templates rather than serving standalone pages. `layout.html` is the base shell rendering the `content` template; `partials.html` holds shared fragments (`boardFragment`, `chatSnapshot`, `chatToolDetail`, `chatDiff`, `taskDetail`, `planDetail`, `reviewDetail`, `ledgerDetail`, `banner`) for htmx-swapped responses. Server data lives under `.Data`, htmx attributes drive interactivity, and custom funcs (`statusClass`, `base`, `markdown`, `statusRank`) are registered by the Go renderer. The renderer parses per-page sets (`index`, `board`, `explorer`, `opencode`, `settings`, `setup` — page + `layout.html`, plus `partials.html` for the board) and a layout-free `partial` set (`partials.html` + `explorer.html`) for htmx fragment responses — keep `define` names unique within each set — and when an edit looks unapplied in the running UI, restart the server before concluding anything (a stale process serves old HTML).
- `index.html` exposes only the opencode-driven "New change session" form (`hx-post="/changes/session"`); the plain "New change" form is gone from the UI (`POST /changes` remains for API clients — do not resurrect the form without a decision). The Discussions list is client-rendered by `app.js`. The Commit all button (`#commit-all-btn`, state from `.Data.GitRepo`/`.Data.GitDirty`) and the `#commit-modal` ids (`commit-file-list`, `commit-stat`, `commit-confirm-btn`, `commit-modal-status`) are wired by id — keep them stable. Two purely server-rendered `.banner.warn` blocks sit above the table, each present only when its view field is non-nil so render tests can assert both states: `#onboarding-banner` (with `#onboarding-dismiss`) from `.Data.OnboardingPending`, and `#spawn-fallback-banner` from `.Data.SpawnFallback`, sentence from `SpawnFallback.Summary` plus a Review settings link.
- `board.html` carries the lifecycle and session controls (`commit-btn`, `close-change-btn`, `reopen-btn`, `sessions-btn`, `new-session-btn`) and the Continue-session button (`#continue-session-btn`) whose label `app.js` flips; the board header renders no add-task/subtask form — task creation happens in agent sessions or via `POST /changes/{id}/tasks`, which remains for API clients (do not resurrect the form without a decision); the drill-down rendering (`.crumbs` from `.Data.Crumbs`, `.card-sub` rollup badge links, `.card-expand[data-expand]`) plus `#board[data-task]` and modal `data-doc` are load-bearing — the chat overlay's Work panel mirrors `#board`/`.cards[data-status]`/`.card[data-task]` and render tests assert them. The worktree strip renders only when `.Data.Worktree` is non-nil: `.worktree-strip[data-state]` with branch/uncommitted/missing/PR pills, a Review button present only beside the `wt-review` pill (`data-review`) that swaps `GET /changes/{id}/review` into `#detail` (the `reviewDetail` fragment), and `#worktree-remove-btn`; the `#sessions-panel` (`#spawn-change-btn`, hidden `#spawn-change-form` with `#spawn-title`/`#spawn-prefix`/`#spawn-artifact`, `#spawn-error`, `#sessions-list`) and the separate `#board-subs` strip ship `hidden` and stay client-populated — the spawn form reloads its `handoff*.md` picker from `GET /changes/{id}/handoffs` on every open and surfaces the server's error message through `#spawn-error`, and `#sessions-list` rows get a client-rendered `from <change>` badge when the sessions payload carries `spawnedFrom`.
- `layout.html`'s header is one sticky `#app-header`. On index and board pages it renders a CSS-hidden `brand` plus `#location-nav` — `#location-back`, `#location-toggle` with `#location-current`, and the `hidden` `#location-menu` dropdown whose `#location-trail` breadcrumb buttons and `.location-actions` wrapper are where the topnavs, bell, and theme toggle actually live on those pages — while every other non-setup page renders the flat `brand | topnav-primary (Changes, Explorer) | topnav-right (#chat-btn, Settings) | #notif-bell | #theme-toggle` directly; `initLocationNav` owns the dropdown, the trail, and `#location-current`. `.active` is applied from `.Page` comparisons, and the Settings link covers the opencode page too. The `brand` anchor renders `<span class="brand-name">{{.ProjectName}}</span>` beside the icon, and the chat overlay's `.chat-head` mirrors the same span as `.chat-project-name`. The Chat button (`#chat-btn`, a real `<button>` before Settings inside the setup guard — render tests pin its presence on app pages and its absence on setup) is wired by id in `app.js`: it POSTs `/chat/session` and opens the chat overlay on the fresh session. The docs bell (`#notif-bell`, `#notif-badge`) opens `#notif-modal` (`#notif-list`, `#docs-refresh-btn`, `#docs-seed-btn`, `#docs-seed-force` + label, `#notif-refresh-status`) — all wired by id in `app.js`. Validation violations render client-side into the layout's `#banner` div (`hidden` default, absent on setup); the `banner` define in `partials.html` has no invoker — no handler or template executes it.
- `layout.html` also owns the chat overlay (`#chat-overlay` — one `.chat-window` carrying `data-chat-view` whose `data-chat-view-panel` panels — the chat main, `#chat-agents`, `#chat-controls-sheet`, and the Work panel `#chat-tasks` — ship `hidden` and stay client-populated) and the `#detail` modal container, present only on index and board pages. The chat main carries the whole composer contract: `#chat-family-bar`, `#chat-transcript`, `#chat-inbox`, `#chat-status`, and `#chat-composer-shell` with the `#chat-composer` form — `#chat-prompt`, the `#chat-more-menu` quick actions (`#chat-plan-btn` targeting `#detail` via htmx, `#chat-tasks-btn`, `#chat-controls-btn`, `#chat-compact-btn`), `#chat-more-btn` with its `#chat-context-usage` ring, `#chat-send-btn`, `#chat-form-host` above the composer, `#chat-reference-picker`, and `#chat-draft-files`/`#chat-skill-chips` — all wired by id in `app.js`, so renames move template and JS together. The setup page renders chrome-free via `{{if ne .Page "setup"}}` guarding the navs, bell, and banner (the location nav is additionally index/board-only): any new global header element must respect those conditionals. Vendored htmx and Sortable stay at pinned `?v=1`; only `app.css`/`app.js` use the content-hashed `.AssetsV`.
- `layout.html`'s `<head>` emits `{{.AccentStyle}}` — the server-rendered inline `<style>` (id `accent-style`) setting `--accent`/`--accent-hover` for `:root` and `[data-theme="light"]` — so templates never hardcode palette colors; keep the emission intact, since `app.js`'s accent picker live-previews by rewriting that element's text. Brand `<link>`s and `.brand-icon` `<img>`s point at the dynamic accent-rendered routes (`/icon.svg`, `/favicon.ico`, `/apple-touch-icon.png`), not static files. The `<title>` is exactly `{{.ProjectName}}` on every page — per-page `pageData.Title` is still populated by call sites but no longer feeds the title element.
- `explorer.html` defines `content`, the dirs-only `explorerTree`/`explorerNode` fragments, and `explorerDetail`: a split shell where each `<summary>` carries `hx-get="/explorer/detail?dir={{.Rel}}"` targeting `#explorer-detail`, every `<details>` keeps `data-rel` so refreshes restore open nodes, and the recursive `{{template "explorerNode" .}}` reference must stay intact. Templates read `.Data.Enabled`/`.RepoName`/`.Root`/`.Dirs`/`.Files`/`.Purpose`/`.Blurb` from the view models in `internal/server/explorer.go`; a missing purpose or blurb renders a muted placeholder, `Enabled=false` renders the disabled error-box pointing at `lessmess init`/`docs seed`, and the detail header carries the `.explorer-chat` button (`data-dir`) for per-directory chats.
- `taskDetail`, `planDetail`, `reviewDetail`, and `ledgerDetail` share one modal shape: `.modal-head` — whose close control is a back-styled `.modal-close.detail-back` button (`data-close-detail`) — then `.modal-panes` holding an empty `<nav class="modal-toc" hidden>` (`app.js` populates it — it must stay present in all four) and `.modal-body.prose` rendered with `{{markdown .Body}}`. `taskDetail` and `ledgerDetail` also carry the modal's `data-doc` href context, which `app.js` resolves relative `.md` links against — nested `tasks/…` paths route by last segment, so a ledger tail opens that container's ledger, a generated view served at `/changes/{id}/ledger` rather than a file on disk. `taskDetail` additionally renders the `data-task-status-control` strip — a `#task-status-<id>` select with `data-task-status`, a `data-open-subtasks` View-subtasks button when subtasks exist, and a live status message span — so task status changes without leaving the modal. `reviewDetail` shows the change's review.md resolved through the worktree overlay; for HTML clients a not-yet-written review renders a server-provided empty-state body instead of a 404.
- `chatSnapshot` is the chat transcript's whole swap unit: its root `.chat-snapshot` carries `data-session`/`data-busy`/`data-page` for the poller, and hidden marker spans (`data-message`, `data-message-type`, `data-message-status`) drive client state such as compaction tracking and pending user boundaries — keep them rendering even though they are invisible. Activity blocks aggregate reasoning/tool/shell lines into `<details data-chat-expand-key>` groups whose tool and turn-diff bodies stay lazy (`data-chat-detail-url` + `.chat-lazy-detail`, filled on expand from `chatToolDetail`/`chatDiff`), unknown message parts render a safe "Unsupported message part" fallback, and forms ship as complete step-by-step wizards — per-field step sections, a review section, an Other custom-answer row, and prev/close/next/submit nav buttons — inside the snapshot so `app.js` can relocate the active one into `#chat-form-host` while preserving state across snapshot swaps.
- `index.html`'s six data `<th>`s wrap `button.sort-btn[data-sort-col]` with a `span.sort-ind`, and each body `<tr>` carries `data-tasks`, `data-status-rank` (`{{.Status | statusRank}}`), and `data-updated` — keep the attribute names and the `statusRank` pipe intact, since `app.js` sorts on them and `render_test.go` asserts them.
- `settings.html` (parsed into its own `renderer.settings` set) is scope strip → split → footer with six `.settings-section[data-section]` blocks (general, session, prompts, git, ui, docs) whose `data-section`/`data-group` values double as `lessmess.json` keys and `initSettings` PUT payload keys — rename them in template, nav, and JS together. The `.scope-seg` labels are exactly `Project`/`Personal` over visually hidden `input[name="settings-scope"]` radios (values `project`/`personal`, Project checked) that must stay for `initSettings` and `render_test.go`; the layer-explanation strings in `settings-foot` are test-asserted too.
- `settings.html` hooks are addressed by id — `#settings-page`, `#settings-load-error`, `#settings-options-hint`, `#settings-agent-list`, `#settings-model-list`, `.src-badge`, `.settings-status`, `#opencode-default-note` with `#opencode-default-text` and its `#align-default-agent` button — and fields expose `data-field`/`data-kind` plus `[data-input]`. The `session.agent` field carries that divergence note: a `hidden` `.banner.warn` shipped empty (its `#align-default-agent` button hidden too), which `app.js` fills from `view.opencodeDefaultAgent` and unhides only when the declared `default_agent` differs from the effective `session.agent`. The `general` block is a real editable section: the Project name string field (`data-field="general.projectName"`, `data-kind="string"`) with source badge, ✦ change button, and a section `[data-save]`; an empty input means the folder default (placeholder/fallback from `view.defaultProjectName`), a successful general save reloads the page so the server-rendered brand and tab title pick up the name, and the wizard re-run is a plain link below the field; the docs section holds the `docs.autoGardenerOnClose`/`docs.gardenerModel` fields plus the `#docs-exclusions` widget, saved through its own `#docs-exclusions-save`/`#docs-exclusions-status` pair outside the per-section `[data-save]` PUT; the ui section's Accent field (`data-field="ui.accent"`, `data-kind="accent"`) is an initially empty `<div class="accent-swatches" data-input data-value="">` that `app.js` fills, beside a `hidden` `.accent-shadow-note` paragraph `app.js` unmasks when a Personal override shadows the Project scope.
- `setup.html` (parsed into its own `renderer.setup` set) defines `content` for the six-step wizard: `data-step` sections `prereqs`, `name`, `bootstrap`, `agent`, `docs`, `finish` with matching `data-step-nav` items, and inner controls (`#setup-prereq-list`, `#setup-recheck-btn`, `#setup-project-name`, `setup-name-scope` radios with Project checked, `#setup-name-save`/`#setup-name-skip` + `#setup-name-status`, the agent step's `#setup-agent`/`#setup-model` over `#setup-agent-list`/`#setup-model-list` datalists with `#setup-options-hint` and a `setup-scope` radio group (Personal checked), `#setup-exclude-list`, seed progress, step buttons) that are all `initSetup` DOM hooks — renames move template and `app.js` together. `GET /setup` renders it even on fully initialized repos.
- `opencode.html` defines only `content` for the OpenCode management page (parsed with `layout.html` into the `renderer.opencode` set): anchored sections (`#oc-status-section`, `#oc-connections-section`, `#oc-mcp-section`, `#oc-permissions-section`) under the `.oc-management-nav`, status cards keyed by `data-oc-section` with `data-oc-body` slots, the `<dialog id="oc-integration-dialog">` for connection flows, and `#oc-return-chat` — every `oc-*` id is an `initOpencodeStatus` hook in `app.js`, and the page renders with full page chrome (it is not the setup page).
