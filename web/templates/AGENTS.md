# web/templates

<!-- tasktracker:begin -->
- Purpose: Go `html/template` sources for the lessmess web UI; each file defines named templates rather than serving standalone pages. `layout.html` is the base shell rendering the `content` template; `partials.html` holds shared fragments (`chatSnapshot`, `chatToolDetail`, `chatDiff`, `taskDetail`, `planDetail`, `reviewDetail`, `ledgerDetail`, `banner`) for htmx-swapped and client-injected responses. Server data lives under `.Data`, htmx attributes drive interactivity, and custom funcs (`statusClass`, `base`, `markdown`, `statusRank`, plus a per-renderer `bp` mount-prefix func) are registered by the Go renderer. The renderer parses one set per page (`index`, `explorer`, `settings`, `opencode`, `setup`, `projects` — page + `layout.html`) and a layout-free `partial` set (`partials.html` + `explorer.html`) for fragment responses — keep `define` names unique within each set — and when an edit looks unapplied in the running UI, restart the server before concluding anything (a stale process serves old HTML; template and static changes need a rebuild to be visible at all).
- Base-path contract: `layout.html` emits `<body data-page="{{.Page}}" data-base="{{.BasePath}}" data-project-name="{{.ProjectName}}">` — `app.js` reads `page` and `BASE` from it once — and every page template prefixes its `href`/`src`/`hx-*` URLs with `{{.BasePath}}`. The layout-free `partial` set renders with a non-pageData dot, so its URLs come from the `bp` func (`explorer.html` tree nodes) or server-prebuilt absolute fields (`data-chat-detail-url`); the same markup serves hub mode (mounted at `/p/<slug>/`) and single-project mode, an empty base emits byte-identical legacy output (pinned by tests), and a root-absolute client URL in any template is a bug.
- `index.html` is the changes card list: the only form is the opencode-driven "New change session" one (`hx-post="{{.BasePath}}/changes/session"`); the plain "New change" form is gone from the UI (`POST /changes` remains for API clients — do not resurrect the form without a decision). `#change-sort` offers the five fixed orders, and `#change-cards` renders one `a.change-card[data-change]` per change carrying `data-tasks`, `data-status-rank` (`{{.Status | statusRank}}`), `data-updated`, and `data-title` — `app.js` sorts and SSE-refreshes from those attributes (`buildChangeCard` mirrors this markup), `render_test.go` asserts them, and the old sortable table (`change-table`/`sort-btn`) must not return. The Discussions list (`#discussions-list`) is client-rendered. The Commit all button (`#commit-all-btn`, state from `.Data.GitRepo`/`.Data.GitDirty`) and the `#commit-modal` ids (`commit-file-list`, `commit-stat`, `commit-confirm-btn`, `commit-modal-status`) are wired by id — keep them stable. Two purely server-rendered `.banner.warn` blocks sit above the list, each present only when its view field is non-nil so render tests can assert both states: `#onboarding-banner` (with `#onboarding-dismiss`) from `.Data.OnboardingPending`, and `#spawn-fallback-banner` from `.Data.SpawnFallback`, sentence from `SpawnFallback.Summary` plus a Review settings link.
- Templates render no change board: `GET /changes/{id}` HTML requests (full page or htmx) redirect to `{{.BasePath}}/?change=<id>` (any `?session=` rides along) and only the JSON API survives, so `index.html` is the sole HTML surface for a change — `app.js` strips the deep-link params and opens the session in Chat, and `?task=` drill-down scope lives in the chat Work panel (JSON `GET /changes/{id}/tasks?task=`). There is no kanban, sessions panel, spawn form, or subagent strip markup anywhere in the tree — the chat overlay's Work panel and Sessions sheet (its change footer's worktree strip included) are client-rendered from JSON feeds instead, and the handoff spawn stays an agent-driven API flow with no UI affordance.
- `layout.html`'s header is one sticky `#app-header`. Only the index page gets the `has-location` class (CSS hides the `brand` there) and the `#location-nav` markup — `#location-back`, `#location-toggle` with `#location-current`, and the `hidden` `#location-menu` dropdown whose `#location-trail` breadcrumb buttons and `.location-actions` wrapper are where the topnavs and bell actually live on index — while every other page renders the flat `brand | topnav-primary (Changes, Explorer) | topnav-right (#chat-btn, Settings) | #notif-bell | #theme-toggle` directly; `initLocationNav` owns the dropdown, the trail, and `#location-current`. There is no project dropdown: the location trail IS the project level, built client-side from the body's `data-base`/`data-project-name` — hub mode roots at Projects (`/`) with the project's effective name as the second crumb, single-project mode keeps the `Changes` root (render tests pin `id="location-current">Changes<`), and the change crumb appears only while a change-bound session is open. `.active` is applied from `.Page` comparisons, and the Settings link covers the opencode page too. The `brand` anchor renders `<span class="brand-name">{{.ProjectName}}</span>` beside the icon, and the chat overlay's `.chat-head` mirrors the same span as `.chat-project-name`. The Chat button (`#chat-btn`, a real `<button>` before Settings inside the page guard — render tests pin its presence on app pages and its absence on setup) is wired by id in `app.js`: it POSTs `/chat/session` and opens the chat overlay on the fresh session. The docs bell (`#notif-bell`, `#notif-badge`) opens `#notif-modal` (`#notif-list`, `#docs-refresh-btn`, `#docs-seed-btn`, `#docs-seed-force` + label, `#notif-refresh-status`) — all wired by id in `app.js`. Validation violations render client-side into the layout's `#banner` div (`hidden` default, absent on setup); the `banner` define in `partials.html` has no invoker — no handler or template executes it.
- `layout.html` also owns the chat overlay (`#chat-overlay` — one `.chat-window` carrying `data-chat-view` whose `data-chat-view-panel` panels — the chat main, `#chat-agents`, `#chat-controls-sheet`, `#chat-sessions-sheet`, and the Work panel `#chat-tasks` — ship `hidden` and stay client-populated) and the `#detail` modal container, present only on the index page. The chat main carries the whole composer contract: `#chat-family-bar`, `#chat-transcript`, `#chat-inbox`, `#chat-status`, and `#chat-composer-shell` with the `#chat-composer` form — `#chat-prompt`, the `#chat-more-menu` quick actions (`#chat-plan-btn` targeting `#detail` via htmx, `#chat-tasks-btn`, `#chat-sessions-btn`, `#chat-controls-btn`, `#chat-compact-btn`), `#chat-more-btn` with its `#chat-context-usage` ring, `#chat-send-btn`, `#chat-form-host` above the composer, `#chat-reference-picker`, and `#chat-draft-files`/`#chat-skill-chips` — all wired by id in `app.js`, so renames move template and JS together. The sessions sheet's hooks work the same way: `#chat-sessions-list` (rows get a client-rendered `from <change>` badge when the sessions payload carries `spawnedFrom`), `#chat-session-new-btn`, `#chat-sessions-worktree`, `#chat-sessions-error`, and the `#chat-change-commit-btn`/`#chat-change-close-btn`/`#chat-change-reopen-btn`/`#chat-change-worktree-remove` actions. The setup page renders chrome-free via `{{if ne .Page "setup"}}` guarding the banner and `{{if and (ne .Page "setup") (ne .Page "projects")}}` guarding the navs and bell (the location nav is additionally index-only; the theme toggle renders on every page): any new global header element must respect those conditionals. Vendored htmx and Sortable stay at pinned `?v=1`; only `app.css`/`app.js` use the content-hashed `.AssetsV`.
- `layout.html`'s `<head>` emits `{{.AccentStyle}}` — the server-rendered inline `<style>` (id `accent-style`) setting `--accent`/`--accent-hover` for `:root` and `[data-theme="light"]` — so templates never hardcode palette colors; keep the emission intact, since `app.js`'s accent picker live-previews by rewriting that element's text. Brand `<link>`s and `.brand-icon` `<img>`s point at the dynamic accent-rendered routes (`/icon.svg`, `/favicon.ico`, `/apple-touch-icon.png`), not static files. The `<title>` is exactly `{{.ProjectName}}` on every page — per-page `pageData.Title` is still populated by call sites but no longer feeds the title element.
- `explorer.html` defines `content`, the dirs-only `explorerTree`/`explorerNode` fragments, and `explorerDetail`: a split shell where each `<summary>` carries `hx-get="{{bp}}/explorer/detail?dir={{.Rel}}"` targeting `#explorer-detail`, every `<details>` keeps `data-rel` so refreshes restore open nodes, and the recursive `{{template "explorerNode" .}}` reference must stay intact. Page data reads `.Data.Enabled`/`.RepoName`/`.Root`/`.Dirs`/`.Files`/`.Purpose`/`.Blurb` from the view models in `internal/server/explorer.go`; a missing purpose or blurb renders a muted placeholder, `Enabled=false` renders the disabled error-box pointing at `lessmess init`/`docs seed`, and the detail header carries the `.explorer-chat` button (`data-dir`) for per-directory chats.
- `taskDetail`, `planDetail`, `reviewDetail`, and `ledgerDetail` share one modal shape: `.modal-head` — whose close control is a back-styled `.modal-close.detail-back` button (`data-close-detail`) — then `.modal-panes` holding an empty `<nav class="modal-toc" hidden>` (`app.js` populates it — it must stay present in all four) and `.modal-body.prose` rendered with `{{markdown .Body}}`. `taskDetail` and `ledgerDetail` also carry the modal's `data-doc` href context, which `app.js` resolves relative `.md` links against — nested `tasks/…` paths route by last segment, so a ledger tail opens that container's generated ledger view. `taskDetail` additionally renders the `data-task-status-control` strip — a `#task-status-<id>` select with `data-task-status`, a `data-open-subtasks` View-subtasks button when subtasks exist or a `data-decompose` Decompose button when they don't, and a live status message span — so task state changes without leaving the modal. `reviewDetail` is fed by the review endpoint: a not-yet-written review arrives as a server-provided empty-state body instead of a 404.
- `chatSnapshot` is the chat transcript's whole swap unit: its root `.chat-snapshot` carries `data-session`/`data-busy`/`data-page` for the poller, `{{.OlderCursor}}` renders the server-side history control (`data-chat-load-older`), and hidden marker spans (`data-message`, `data-message-type`, `data-message-status`) drive client state such as compaction tracking and pending user boundaries — keep them rendering even though they are invisible. Activity blocks aggregate reasoning/tool/shell lines into `<details data-chat-expand-key>` groups whose tool and turn-diff bodies stay lazy (`data-chat-detail-url` + `.chat-lazy-detail`, filled on expand from `chatToolDetail`/`chatDiff`), unknown message parts render a safe "Unsupported message part" fallback, and forms ship as complete step-by-step wizards — per-field step sections, a review section, an Other custom-answer row, and prev/close/next/submit nav buttons — inside the snapshot so `app.js` can relocate the active one into `#chat-form-host` while preserving state across snapshot swaps.
- `settings.html` (parsed into its own `renderer.settings` set) is scope strip → split → footer with six `.settings-section[data-section]` blocks (general, session, prompts, git, ui, docs) whose `data-section`/`data-group` values double as `lessmess.json` keys and `initSettings` PUT payload keys — rename them in template, nav, and JS together. The `.scope-seg` labels are exactly `Project`/`Personal` over visually hidden `input[name="settings-scope"]` radios (values `project`/`personal`, Project checked) that must stay for `initSettings` and `render_test.go`; the layer-explanation strings in `settings-foot` are test-asserted too.
- `settings.html` hooks are addressed by id — `#settings-page`, `#settings-load-error`, `#settings-options-hint`, `#settings-agent-list`, `#settings-model-list`, `.src-badge`, `.settings-status`, `#opencode-default-note` with `#opencode-default-text` and its `#align-default-agent` button — and fields expose `data-field`/`data-kind` plus `[data-input]`. The `session.agent` field carries that divergence note: a `hidden` `.banner.warn` shipped empty (its `#align-default-agent` button hidden too), which `app.js` fills from `view.opencodeDefaultAgent` and unhides only when the declared `default_agent` differs from the effective `session.agent`. The `general` block is a real editable section: the Project name string field (`data-field="general.projectName"`, `data-kind="string"`) with source badge, ✦ change button, and a section `[data-save]`; an empty input means the folder default (placeholder/fallback from `view.defaultProjectName`), a successful general save reloads the page so the server-rendered brand and tab title pick up the name, and the wizard re-run and service-status links are plain links in the same section; the docs section holds the `docs.autoGardenerOnClose`/`docs.gardenerModel` fields plus the `#docs-exclusions` widget, saved through its own `#docs-exclusions-save`/`#docs-exclusions-status` pair outside the per-section `[data-save]` PUT; the git section holds `git.defaultBranch` (string over the `#settings-branch-list` branch datalist), the `git.worktrees` tri-state bool select (empty = Inherit, plus On/Off), and `git.reviewModel` (string over the model datalist); the ui section's Accent field (`data-field="ui.accent"`, `data-kind="accent"`) is an initially empty `<div class="accent-swatches" data-input data-value="">` that `app.js` fills, beside a `hidden` `.accent-shadow-note` paragraph `app.js` unmasks when a Personal override shadows the Project scope.
- `setup.html` (parsed into its own `renderer.setup` set) defines `content` for the six-step wizard: `data-step` sections `prereqs`, `name`, `bootstrap`, `agent`, `docs`, `finish` with matching `data-step-nav` items, and inner controls (`#setup-prereq-list`, `#setup-recheck-btn`, `#setup-project-name`, `setup-name-scope` radios with Project checked, `#setup-name-save`/`#setup-name-skip` + `#setup-name-status`, the agent step's `#setup-agent`/`#setup-model` over `#setup-agent-list`/`#setup-model-list` datalists with `#setup-options-hint` and a `setup-scope` radio group (Personal checked), `#setup-exclude-list`, seed progress, step buttons) that are all `initSetup` DOM hooks — renames move template and `app.js` together. `GET /setup` renders it even on fully initialized repos.
- `opencode.html` defines only `content` for the OpenCode management page (parsed with `layout.html` into the `renderer.opencode` set): anchored sections (`#oc-status-section`, `#oc-connections-section`, `#oc-mcp-section`, `#oc-permissions-section`) under the `.oc-management-nav`, status cards keyed by `data-oc-section` with `data-oc-body` slots, the `<dialog id="oc-integration-dialog">` for connection flows, and `#oc-return-chat` — every `oc-*` id is an `initOpencodeStatus` hook in `app.js`, and the page renders with full page chrome (it is not the setup page).
- `projects.html` (parsed with `layout.html` into its own `renderer.projects` set) is the hub-only landing page: `#projects-page` lists one `.project-row[data-slug][data-status]` per registered project — a `.project-link` (name, path, and an extra `.project-detail` span for non-`ready` slots), a status pill, and a `.project-remove[data-slug]` button — over the `#project-add-form` (`#project-add-path` input plus `#project-add-status`); `initProjects` POSTs/DELETEs `/api/projects` and reloads on success. The page renders brand and theme toggle only (no navs, location nav, or chat button) and drives no SSE.
