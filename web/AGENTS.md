# web

<!-- tasktracker:begin -->
- Purpose: Go package holding the lessmess web UI's embedded assets — `templates/` (html/template sources) and `static/` (CSS, JS, and the vendored htmx library; see `static/VENDOR.md` before updating it). `web.go` is the whole package: `FS embed.FS` via `//go:embed templates static` — new files under those trees are picked up automatically, but a new top-level path must be added to the embed list, and files must exist at build time.
- Root `agentsdocs.json` excludes only `web/static`, so all JS/CSS behavior described here sits outside docs coverage while `templates/` stays covered. `layout.html` parses with each page template into per-page template sets (index, explorer, settings, opencode, setup, and projects each get their own `renderer` field), all sharing the `content` template; conventions live in `templates/AGENTS.md`.
- Every client-side URL is built from one injected base: `layout.html` emits `<body data-base="{{.BasePath}}" data-project-name="{{.ProjectName}}">`, `app.js` reads it once as `BASE`, and all `fetch` calls and `new EventSource(BASE + "/events")` concatenate it while templates prefix their `href`/`src`/`hx-*` attributes with `{{.BasePath}}` — the same markup serves hub mode (mounted at `/p/<slug>/`) and legacy single-project mode (empty base, byte-identical output), and a root-absolute client URL is always a bug. The location trail consumes the same attributes: `locationBaseTrail()` branches on `BASE`, hub mode rooting at Projects (`/`) with the project's effective name as the second crumb (→ `<base>/`), legacy keeping the `Changes` root — there is no project dropdown. `projects.html` is the hub-only landing/management page (its own page kind parsed with `layout.html`, no SSE on it), and its add/remove calls `/api/projects`.
- Index refresh rules: `fs`/`write` events on the shared `/events` SSE stream land in `scheduleRefresh` (a 250 ms debounce), which runs `checkValidation` and, on the index page, either `followSession()` — when the Chat overlay is open with an active session it polls the session→change mapping and navigates to `/?change=<id>&session=<sid>` once the discussion scaffolds, skipping the refresh entirely until then so the open transcript is never clobbered — or `refreshChangeCards()`, which rebuilds the card list in place from `/`'s JSON view (no page reload while a chat may be open). The same events re-sync the open Chat's Work panel (`loadSessionTasks`/`resolveSessionTasks`).
- The shared header is a sticky `#app-header` (52px, z-index 50) whose `.active` states are applied server-side from `pageData.Page` (the Settings link is active on the opencode page too), under the z-index ladder notif/commit modals 25 < chat overlay 30 < `#detail` 40 < header 50 < `#location-menu` 70 — keep new fixed/sticky surfaces inside that ladder. The header Chat button (`#chat-btn`, inside the page-chrome guard so it is absent on setup and projects) is wired in the shared init path so it works on every page: it POSTs `/chat/session` (disabled while pending, server error alerted) and opens the fresh session with `openChat`; `openPreferredSession` is a one-line alias of `openChat` — Chat is the only surface any session ever opens in.
- Chat is the whole session UI: `openChat` fetches a full server-normalized transcript snapshot from `/api/sessions/{id}/chat`, and `pollChat` re-fetches that snapshot every ~1.2s while the overlay is visible — one in-flight request (overlaps aborted), paused while `document.hidden`, no event stream for chat. Every mutation — send, interrupt, permission decisions (once/always/reject), form answers, usage, controls, references, fork/revert/compact/rename/export/delete — posts to an explicit `/api/sessions/{id}/chat/*` subroute that authenticates to OpenCode server-side, so credentials never reach the browser or the JS. A poll swaps the transcript only when the snapshot HTML actually changed, and the swap is lossless by construction: loaded history pages and their cursor are re-inserted, open lazy details (tool output and turn diffs load on expand from `data-chat-detail-url`) are restored and refetched, in-progress form state is captured and restored, scroll sticks to the bottom when near it and is otherwise preserved (with per-session scroll memory), and unsent drafts are kept per session (`cstate.drafts`).
- Chat auxiliary surfaces: on desktop exactly one drawer is open at a time (`requestChatAuxiliary` closes work/agents/controls before opening another); at ≤840px `compactChatUI()` swaps full-screen `data-chat-view` views on a stack (`openChatView`/`closeChatView`, the chat back control pops the top view). `syncChatModalInert` inerts everything behind the overlay — or behind `#detail` when a modal stacks over Chat — except `#app-header`, and `syncChatViewport` mirrors `visualViewport` into CSS vars so the composer tracks the virtual keyboard.
- The composer row is the chat's action hub: the `#chat-action-pill` (`data-mode`/`data-segments`/`data-expanded`) hosts `#chat-send-btn` plus segment buttons swapped in by state — cancel/steer/queue while composing or busy, copy/fork/revert for a selected message — the `#chat-more-btn` context-usage ring opens the `#chat-more-menu` quick actions (Plan targets `#detail` via htmx, Tasks, Runtime, and Compact — which gates on reported usage plus lifecycle capabilities), pending forms are relocated from the snapshot into `#chat-form-host` above the composer (`mountChatForm`; dismissing one fires an interrupt), references picked from `/chat/references` and attached skills render as chips in `#chat-draft-files`/`#chat-skill-chips`, and queued/steering follow-ups render as `data-inbox-id` rows in a client-created `#chat-pending-messages` host inside the transcript (the lifecycle `/inbox` feed, capability-gated, with the pill's cancel/fork/revert acting on the selection). The overlay also carries `#chat-revert-dialog`, the confirm modal behind a message's Revert action.
- The detail modal navigates in-modal, entirely client-side: `buildDetailTOC()` fills the `.modal-toc` rail from h2/h3 ids (hidden under 2 headings, toggles `has-toc` which widens the modal), an rAF-throttled scroll-spy runs on `.modal-body`, and a delegated click handler keeps relative `.md` links in-modal by mapping them against the modal's `data-doc` context (`plan.md`, `(../)ledger.md`, nested `tasks/...` files, cross-change plans) — keep that mapping exhaustive when adding nested link shapes.
- The card list is sorted and filtered client-side over the cards' `data-tasks`/`data-status-rank` (numeric), `data-updated` (string), and `data-title` attributes — never display text: `#change-sort` offers five fixed orders persisted to localStorage `tt-index-sort` as a `col:dir` string (corrupt or unknown values fail open to the server's newest-first default), and `#change-filter-status` persists to `tt-index-filter-status`, hiding non-matching cards, rewriting per-status counts into the option labels, and toggling `#change-cards-empty`. Tapping a card (plain left click only — the `href` stays for modified clicks) runs `resumeChangeSession`: continue the change's `tt-last-session:<change>` session when it still exists, else the newest, else create one. The Commit all flow (`initCommitAll`) fetches `/api/git/status`, renders merged porcelain rows with per-file `+/-` counts, posts `/api/git/commit` on confirm, and polls `/api/git/commit-status` until done.
- The explorer's client behavior: a `docs` SSE listener refreshes `#explorer-tree` and restores open nodes, selection is tracked client-side with `#explorer-detail` re-fetched per directory, tree fragments injected via `innerHTML` must pass through `htmx.process`, and the `.explorer-chat` handler runs in the capture phase from the detail header. The docs bell and findings modal are client-rendered by `checkValidation` (findings cached, banner is violations-only, badge re-renders on `tt:docs-event`); the modal's refresh button posts `/docs/refresh` and its seed button relabels "Run missing docs (N dirs)" from `/api/validate`'s `docsSeedPending` — both disable while running and re-enable on the next docs SSE event.
- The settings editor contract: `initSettings` finds every hook (`#settings-page`, scope radios, `.settings-nav` + `data-group`, `data-field`/`data-kind`/`[data-input]`, section `[data-save]`, source badges, datalists, `#opencode-default-note`/`#opencode-default-text` with the `#align-default-agent` button) — reshape `settings.html`/`app.css` freely but keep those hooks; the `general` section carries the project-name string field and `[data-save]`, and a successful general save reloads the page so the server-rendered brand and tab title pick up the new name; the divergence note unhides only when `view.opencodeDefaultAgent.declared` differs from the effective `session.agent`, and its Align button POSTs `/api/settings/opencode-default-agent` then reloads the settings view; agent/model inputs are `<datalist>` comboboxes that stay free text so settings remain editable offline. The docs section adds a runtime status line fed by `/docs/status` (`#docs-runtime-status`, with `#docs-initialize-btn` POSTing `/docs/initialize` and states for unreadable config, uninitialized coverage, restart-required, and active) beside the `docs.enabled` tri-state, and the `#docs-exclusions` editor (lazy folder tree from `/api/setup/dirs`) saves through its own `POST /docs/exclusions`, disabled until docs are enabled. The OpenCode management page (`initOpencodeStatus`, linked from the general section) fills the `data-oc-section`/`data-oc-body` status cards plus its connections/MCP/permissions sections with runtime state only — lessmess never stores keys — and its Return-to-Chat button simply clicks `#chat-btn`.
- The setup wizard's client logic (`initSetup`) drives five steps — prereqs, name, bootstrap, agent, finish — gating Continue on `ready` (only `fail` prereqs block); the name step prefills `#setup-project-name` from `GET /api/settings`'s effective value (its Save PUTs `{general:{projectName}}` to the scope the radios pick; skip continues unsaved), the bootstrap step POSTs an empty body to `/api/setup/bootstrap` (merge-safe and idempotent — already-initialized repos may re-run it), the agent step loads options only after prereqs discover the service (`#setup-options-hint` when unavailable) and saves `session.agent`/`session.model` per scope, and finish POSTs `/api/setup/complete` with per-step marks before navigating to `/`. There is no docs step — coverage initialization and exclusions live in Settings.
- Theming follows the accent: the `--accent`/`--accent-hover` pair arrives via the server-injected inline `<style>` (`{{.AccentStyle}}`, palette from `internal/server/accent.go`) and derivatives `color-mix` from `var(--accent)` — the only sanctioned hex literals are the theme-block fallback definitions of `--accent`. The Settings accent picker is the `data-kind="accent"` field: swatch chips built from `/api/settings/options`, a pending pick kept on the container's `data-value` behind the `accentTouched` guard (`render()` must not overwrite it mid-pick) and live-previewed by rewriting the head `#accent-style` element from the four hexes the options payload carries per entry; `syncAccentValues()` is the single reset point (initial load, scope switch, save success), `""` clears to Auto (Auto in both layers re-rolls server-side), and a `.accent-shadow-note` fires when the Project scope is shadowed by a Personal override.
- There is no change board anywhere — not in the templates and not client-rendered. A change is entered two ways: tapping its index card, or a `/?change=<id>[&session=<sid>]` deep link (`initChangeDeepLink` strips the params and opens/resumes the session; `/changes/{id}` HTML requests, htmx included, redirect there server-side). All change-scoped UI lives in the chat overlay: the Work panel renders `/changes/{id}/tasks` JSON (`?task=` adds a subtask-scope row; plan and task rows htmx into `#detail`) and re-syncs on SSE; the Sessions sheet is the change's action surface — session list with `from <change>` badges from `spawnedFrom`, a new-session POST to `/changes/{id}/sessions`, a worktree strip built only when the payload carries `worktree` (branch pill, `uncommitted`/`worktree missing` state flags, an external PR link, a review pill htmx-loading `/changes/{id}/review` into `#detail`), and the commit/close/reopen/worktree-remove actions whose failures surface in `#chat-sessions-error`; the handoff spawn stays an agent-driven API flow with no UI affordance.
