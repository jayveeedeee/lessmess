# web

<!-- tasktracker:begin -->
- Purpose: Go package holding the lessmess web UI's embedded assets — `templates/` (html/template sources) and `static/` (CSS, JS, and the vendored htmx and Sortable libraries; see `static/VENDOR.md` before updating them). `web.go` is the whole package: `FS embed.FS` via `//go:embed templates static` — new files under those trees are picked up automatically, but a new top-level path must be added to the embed list, and files must exist at build time.
- Root `agentsdocs.json` excludes only `web/static`, so all JS/CSS behavior described here sits outside docs coverage while `templates/` stays covered. `layout.html` parses with each page template into per-page template sets (`renderer.settings` and `renderer.setup` are separate from the board/index set), all sharing the `content` template; conventions live in `templates/AGENTS.md`.
- Index refresh rules: `fs`/`write` events on the shared `/events` SSE stream trigger `scheduleRefresh`, which full-reloads the index — but never while the Chat overlay is open with an active session: `followSession()` polls the session→change mapping and navigates to `/changes/<id>?session=<sid>` once the discussion scaffolds, and until the session binds, the reload is skipped entirely so the open transcript is never clobbered. Boards are immune — they refresh via `refreshBoard()`'s htmx fragment re-request — and an open Chat's Work panel re-syncs its tasks on the same events.
- The shared header is a sticky `#app-header` (52px, z-index 50) whose `.active` states are applied server-side from `pageData.Page` (the Settings link is active on the opencode page too), under the z-index ladder notif/commit modals 25 < chat overlay 30 < `#detail` 40 < header 50 < `#location-menu` 70 — keep new fixed/sticky surfaces inside that ladder. The header Chat button (`#chat-btn`, inside the setup guard) is wired in the shared init path so it works on every page: it POSTs `/chat/session` (disabled while pending, server error alerted) and opens the fresh session with `openChat`; `openPreferredSession` is a one-line alias of `openChat` — Chat is the only surface any session ever opens in.
- Chat is the whole session UI: `openChat` fetches a full server-normalized transcript snapshot from `/api/sessions/{id}/chat`, and `pollChat` re-fetches that snapshot every ~1.2s while the overlay is visible — one in-flight request (overlaps aborted), paused while `document.hidden`, no event stream for chat. Every mutation — send, interrupt, permission decisions (once/always/reject), form answers, usage, controls, references, fork/revert/compact/rename/export/delete — posts to an explicit `/api/sessions/{id}/chat/*` subroute that authenticates to OpenCode server-side, so credentials never reach the browser or the JS.
- A poll swaps the transcript only when the snapshot HTML actually changed, and the swap is lossless by construction: loaded history pages and their cursor are re-inserted, open lazy details (tool output and turn diffs load on expand from `data-chat-detail-url`) are restored and refetched, in-progress form state is captured and restored, scroll sticks to the bottom when near it and is otherwise preserved (with per-session scroll memory), and unsent drafts are kept per session (`cstate.drafts`).
- Chat auxiliary surfaces: on desktop exactly one drawer is open at a time (`requestChatAuxiliary` closes work/agents/controls before opening another); at ≤840px `compactChatUI()` swaps full-screen `data-chat-view` views on a stack (`openChatView`/`closeChatView`, the chat back control pops the top view). `syncChatModalInert` inerts everything behind the overlay — or behind `#detail` when a modal stacks over Chat — except `#app-header`, and `syncChatViewport` mirrors `visualViewport` into CSS vars so the composer tracks the virtual keyboard.
- The composer row is the chat's action hub: one `#chat-send-btn` flips between send and stop (`data-action`, derived from busy state plus composer focus), the `#chat-more-btn` context-usage ring opens the `#chat-more-menu` quick actions (Plan targets `#detail` via htmx, Tasks, Runtime, and Compact — which gates on reported usage plus lifecycle capabilities), pending forms are relocated from the snapshot into `#chat-form-host` above the composer (`mountChatForm`; dismissing one fires an interrupt), references picked from `/chat/references` and attached skills render as chips in `#chat-draft-files`/`#chat-skill-chips`, and queued follow-ups render in `#chat-inbox`.
- The detail modal navigates in-modal, entirely client-side: `buildDetailTOC()` fills the `.modal-toc` rail from h2/h3 ids (hidden under 2 headings, toggles `has-toc` which widens the modal), an rAF-throttled scroll-spy runs on `.modal-body`, and a delegated click handler keeps relative `.md` links in-modal by mapping them against the modal's `data-doc` context (`plan.md`, `(../)ledger.md`, nested `tasks/...` files, cross-change plans) — keep that mapping exhaustive when adding nested link shapes.
- The index table is sortable client-side (`initIndexSort`): header clicks sort rows from `data-*` attributes (`data-tasks` — the server-computed recursive task count, rendered `x/y` — and `data-status-rank` numeric, `data-updated` string, cell text otherwise), toggle `sort-asc`/`sort-desc` plus `aria-sort`, and persist `{col, dir}` to localStorage `tt-index-sort`, re-applied on every load; corrupt stored values fail open to the server's newest-first default. The Commit all flow (`initCommitAll`) fetches `/api/git/status`, renders merged porcelain rows with per-file `+/-` counts, posts `/api/git/commit` on confirm, and polls `/api/git/commit-status` until done.
- The explorer's client behavior: a `docs` SSE listener refreshes `#explorer-tree` and restores open nodes, selection is tracked client-side with `#explorer-detail` re-fetched per directory, tree fragments injected via `innerHTML` must pass through `htmx.process`, and the `.explorer-chat` handler runs in the capture phase from the detail header. The docs bell and findings modal are client-rendered by `checkValidation` (findings cached, banner is violations-only, badge re-renders on `tt:docs-event`); the modal's refresh button posts `/docs/refresh` and its seed button relabels "Run missing docs (N)" from `/api/validate`'s `docsSeedPending` — both disable while running and re-enable on the next docs SSE event.
- The settings editor contract: `initSettings` finds every hook (`#settings-page`, scope radios, `.settings-nav` + `data-group`, `data-field`/`data-kind`/`[data-input]`, section `[data-save]`, source badges, datalists, `#opencode-default-note`/`#opencode-default-text` with the `#align-default-agent` button) — reshape `settings.html`/`app.css` freely but keep those hooks; the `general` section carries the project-name string field and `[data-save]`, and a successful general save reloads the page so the server-rendered brand and tab title pick up the new name; the divergence note unhides only when `view.opencodeDefaultAgent.declared` differs from the effective `session.agent`, and its Align button POSTs `/api/settings/opencode-default-agent` then reloads the settings view; agent/model inputs are `<datalist>` comboboxes that stay free text so settings remain editable offline. The OpenCode management page (`initOpencodeStatus`, linked from the general section) fills the `data-oc-section`/`data-oc-body` status cards plus its connections/MCP/permissions sections with runtime state only — lessmess never stores keys — and its Return-to-Chat button simply clicks `#chat-btn`.
- The setup wizard's client logic (`initSetup`) gates Continue on `ready` (only `fail` prereqs block), prefills the name step's `#setup-project-name` from `GET /api/settings`'s effective value (its Save PUTs `{general:{projectName}}`; Skip continues unsaved), POSTs bootstrap `{docsCoverage, excludeDirs}` (re-submitting updates an existing `agentsdocs.json`), treats docs seeding as opt-in with `/api/setup/docs-seed-status` polling, and uses an exclusion picker whose semantics (top-level = base-name patterns pruning subtrees, nested = exact paths) are shared with the Settings `#docs-exclusions` editor via `POST /docs/exclusions`.
- Theming follows the accent: the `--accent`/`--accent-hover` pair arrives via the server-injected inline `<style>` (`{{.AccentStyle}}`, palette from `internal/server/accent.go`) and derivatives `color-mix` from `var(--accent)` — the only sanctioned hex literals are the theme-block fallback definitions of `--accent`. The Settings accent picker is the `data-kind="accent"` field: swatch chips built from `/api/settings/options`, a pending pick kept on the container's `data-value` behind the `accentTouched` guard (`render()` must not overwrite it mid-pick) and live-previewed by rewriting the head `#accent-style` element from the four hexes the options payload carries per entry; `syncAccentValues()` is the single reset point (initial load, scope switch, save success), `""` clears to Auto (Auto in both layers re-rolls server-side), and a `.accent-shadow-note` fires when the Project scope is shadowed by a Personal override.
- Board interactions: `.card-expand[data-expand]` buttons on leaf cards post `/changes/{id}/expand` (an already-exists 409 still lands there) and navigate to the task's sub-board, container cards instead drill into `?task=` sub-boards through their rollup badge link (`x/y ✓`), and card titles open the nested task detail in-modal — `refreshBoard()` re-requests `location.pathname + location.search`, so SSE fragment swaps keep the drill-down scope — sub-boards render breadcrumbs and scope the sessions panel and Continue button to the exact task (Continue keys `tt-last-session:<change>/<task>`, the panel filters sessions to `task === boardTask()`, and its New session button POSTs that task so the session binds at that level; the board has no task-creation form — tasks are created in sessions or via the API); the close-change confirm warns while any task is not Done or Cancelled (`countOpenTasks()` counts only the visible board — recursive readiness is the server's gate) before posting the lifecycle action, and a board URL's `?session=<id>` makes `autoOpenSession` strip the param and reopen that session in Chat. The chat overlay's Work panel is the same board DOM: `setChatTasks` mirrors `#board`/`.cards[data-status]`/`.card[data-task]` (re-synced on every `htmx:afterSwap`) or fetches the session's bound change via `resolveSessionTasks`, and detail links marked `data-open-subtasks` open it in-chat instead of navigating. The sessions panel's Spawn change flow (`initSpawnChange`) reloads the `handoff*.md` picker from `GET /changes/{id}/handoffs` on every open, POSTs `/changes/{id}/spawn-change` (title, prefix, artifact), surfaces server error messages in `#spawn-error`, opens the spawned session via `openPreferredSession` — Chat, always — and badges `#sessions-list` rows `from <change>` from the payload's `spawnedFrom`. Subagent chips (`refreshSubs` → `renderSubs`, re-run on every board swap) attach sessions carrying `task` to the matching card, fall back to the `#board-subs` strip for `parent`-only sessions, and render dead subs (`live:false`) dimmed but openable through their Chat buttons — the board trusts the server's `task`/`parent` payload fields and never parses titles itself.
